# Net Control

Локальное приложение для Windows с HTML-интерфейсом: принимает экспорт **Traffic Flow** от MikroTik и выделяет подозрительные закономерности в метаданных потоков. Поддерживаются NetFlow v5, NetFlow v9 и IPFIX (v10) с шаблонами. Проверка подключения к RouterOS 7 через REST API необязательна и не включает экспорт автоматически.

## Установка

Откройте вкладку **Actions** в GitHub, выберите успешный запуск **Windows installer** и скачайте артефакт **Net-Control-Windows**. Распакуйте архив и запустите `setup.exe`. Для скачивания артефакта может потребоваться вход в GitHub. Имя `setup.exe` может приводить к автоматическому применению Windows compatibility shims; при необходимости переименуйте файл перед запуском. Установщик не подписан: Windows SmartScreen может показать предупреждение; проверяйте источник файла перед запуском. Установка и запуск выполняются под учётной записью пользователя.

## Начало работы

1. Запустите Net Control на Windows-компьютере, доступном по сети от роутера. Разрешите входящий UDP 2055 в брандмауэре Windows (или выберите другой порт). Ограничьте правило источником — IPv4 роутера.
2. На странице **Подключение** укажите IPv4-адрес MikroTik и UDP-порт, затем нажмите **Запустить сбор**. Сборщик слушает на всех IPv4-интерфейсах, но принимает пакеты только с указанного IP. Сбор запускается вручную при каждом открытии приложения.
3. На RouterOS включите Traffic Flow и укажите адрес Windows-компьютера (не адрес роутера). Пример для RouterOS 7, выполните в терминале, подставив реальный адрес:

   ```routeros
   /ip traffic-flow set enabled=yes interfaces=all
   /ip traffic-flow target add dst-address=192.168.88.10 port=2055 version=9
   ```

   Если target уже существует, измените его вместо добавления дубликата. Настройка `interfaces=all` включает все интерфейсы и может учитывать один и тот же трафик несколько раз; настройте интерфейсы и политику экспорта под свою сеть. Экспорт обычно происходит после завершения потока или по тайм-ауту RouterOS, поэтому данные могут появиться с задержкой. Некоторые конфигурации NAT и интерфейсов меняют видимые адреса.
4. Убедитесь, что на странице обзора увеличивается число UDP-пакетов и потоков. Если пакеты есть, а потоков нет, проверьте версию экспорта и дождитесь повторной отправки шаблонов v9/IPFIX. Проверьте маршрутизацию, адрес источника экспорта и firewall при отсутствии пакетов.

Для опциональной проверки API используйте RouterOS 7, включите `www-ssl`, настройте проверяемый сертификат и ограниченного пользователя с разрешением чтения REST API. Укажите порт HTTPS (обычно 443). Обычный HTTP и разрешение самоподписанного сертификата небезопасны: учётные данные могут быть перехвачены. Не используйте их в недоверенной сети. Пароль не сохраняется на диск. Подключение к API только читает `/rest/system/resource` и не меняет настройки роутера.

## Как работает анализ

В памяти хранится скользящее окно из пяти минут, не более 50 000 последних записей. Время — время получения экспортированной записи, а не реальное начало соединения. Сырые потоки исчезают при закрытии, перезапуске сбора или очистке. Отдельная локальная история событий и агрегатов по умолчанию выключена; при включении хранится на диске. При переполнении отброшенные записи отображаются внизу окна. Доступны суммарные данные и топ-30 источников; показано до 100 сигналов. Счётчики учитывают всё окно. Неподдерживаемые поля игнорируются, неизвестные шаблоны не интерпретируются. Sampling, если он включён на роутере, не компенсируется; цифры могут быть занижены. При высокой нагрузке UDP-пакеты могут теряться до попадания в приложение.

Сигналы работают только при заданных локальных IPv4-подсетях. Анализируются исходящие потоки внутренних хостов и входящие потоки к ним. Стартовые пороги на окно получения записей — настраиваемые:
- сканирование: 30 внешних назначений;
- возможный спам: SMTP к 10 внешним назначениям, за исключением разрешённых почтовых серверов;
- возможный майнинг: 5 записей к характерным портам, или интервал не менее 5 минут по времени потоков к тому же адресу и порту, или совпадение с вручную заданным адресом пула;
- возможный исходящий DDoS: 100 000 экспортированных пакетов и 20 МБ;
- возможная входящая атака: 30 внешних источников и 100 000 экспортированных пакетов к одному локальному хосту.

Можно указать исключённые сети и вручную поддерживаемый список адресов пулов в CIDR. Необходима калибровка порогов и исключений под свою сеть. Уровни «низкое» и «умеренное» — условные градации по силам признаков, а не вероятности заражения; автоматической блокировки нет. При включённой истории для контекста исходящей нагрузки отображается средний объём по наблюдаемым пятиминутным окнам после накопления как минимум 20 окон за 3 разных календарных дня; пустые окна не входят. Это не точный профиль и не единственный критерий сигнала. Смещение времени, неполный экспорт, смена IP и NAT могут исказить сравнение.

Это **не антивирус и не доказательство** наличия вируса, спамера, майнера или DDoS. Для расследования используйте логи роутера, DNS, IDS и проверку устройства; приложение автоматически никого не блокирует. Время в окне — время получения экспорта, а не точное время пакетов; скорость и число соединений не выводятся из числа записей. Учтённые объёмы могут включать дубли, потери и sampling. IPv6-сигналы пока не поддерживаются. Доменные базы и DNS не подключены, имена сайтов и содержимое шифрованных соединений не определяются. Общие IPv4-базы репутации описаны ниже.

## Разработка и сборка

Нужен Node.js 22 и npm. На Windows:

```sh
npm ci
npm test
npm start
npm run dist:win
```

Результат сборки — `dist/setup.exe`. GitHub Actions запускает тесты и собирает x64 NSIS-установщик на `windows-latest` при push или вручную через `workflow_dispatch`. Локальная сборка не отправляет данные в облако; npm/GitHub Actions нужны только для получения зависимостей и сборки.

### Если проверка API показывает ECONNREFUSED

Роутер отклонил TCP-соединение: убедитесь, что указан правильный IPv4 и порт, включена соответствующая служба и доступ не ограничен в `/ip service` или firewall. Для HTTPS нужна служба `www-ssl` (обычно TCP 443), для HTTP — `www` (обычно TCP 80). Фактические порты могут быть изменены; посмотреть состояние можно командой `/ip service print` в терминале RouterOS. При отключённом HTTPS порт 443 чаще всего не подходит. HTTP передаёт пароль открытым текстом; предпочтителен HTTPS с доверенным сертификатом. Проверка REST API поддерживает только RouterOS 7; при этом сам сбор Traffic Flow не зависит от проверки API.

## Направление трафика, анализ хоста и отчёт

В разделе **Подключение → Локальные подсети** укажите все локальные IPv4-подсети в формате CIDR (например, `192.168.88.0/24` и `10.254.100.0/24`, по одной на строку) и сохраните. Список хранится на компьютере в настройках приложения. Существующие потоки окна пересчитываются после изменения. Пустой список не позволяет определить направление: всё отображается как неопределённое. IPv6 также остаётся неопределённым. На обзоре исходящий означает из заданной сети наружу, входящий — извне в заданную сеть, внутренний — между заданными сетями, транзитный — между адресами вне них. Это направление по адресам в экспорте, не физическое направление интерфейса: NAT и экспорт на нескольких интерфейсах могут менять картину или дублировать объём. Укажите все нужные локальные сети и проверьте настройки Traffic Flow.

IP компьютера для Traffic Flow определяется по маршруту ОС до указанного IPv4 роутера; пакеты для определения маршрута не отправляются. Это не проверяет доступность компьютера с роутера. Проверьте адрес и при необходимости выберите интерфейс или введите адрес вручную. `127.0.0.1`/localhost роутеру не подходит: он обозначает сам роутер, а не компьютер со сборщиком.

Нажмите IP в сигнале безопасности или таблице источников, чтобы открыть карточку хоста. В ней показаны потоки в обе стороны относительно IP хоста, раздельные объёмы, предполагаемые типы и последние 200 записей. Период — последние пять минут с момента получения записей. Сортировка таблицы источников применяется ко всем источникам, после чего показываются первые 30; нажмите заголовок ещё раз, чтобы изменить направление.

Классификация почты, IP-телефонии, медиа, P2P, веба, VPN, файловых протоколов и DNS — **только предположение по порту и протоколу**. В обратном потоке рассматривается также порт источника. Любое приложение может использовать другой порт или совпадать с правилом случайно; известные ресурсы и домены не определяются. HTTPS/QUIC остаётся общей категорией, а не классифицируется по конкретным сайтам, видео, мессенджерам или почте. Это не DPI и не анализ содержимого.

Кнопка **Сохранить отчёт** предлагает выбрать путь для автономного HTML-файла. В отчёте — текущее окно, направления, категории, до 100 сигналов, рекомендации, до 30 источников и подробности до 20 самых активных источников (до 20 последних потоков и до 10 контрагентов для каждого). Файл содержит IP-адреса и сведения о сети; храните его как конфиденциальный. Отчёт не отправляется в интернет. Суммы хостов не следует складывать: один поток может присутствовать в карточках обоих участников.

## Обновления и публикация версий

Начиная с версии 1.1.0 установленное Windows-приложение проверяет **стабильные GitHub Releases** этого публичного репозитория при запуске (через 10 секунд) и каждые 6 часов. Если найдена более новая версия, установщик скачивается автоматически и проверяется по SHA-512 из `latest.yml`. Установка выполняется только после подтверждения в разделе **О программе**; при перезапуске потоки из памяти будут потеряны. В разделе есть ручная проверка и подробное встроенное руководство. Режим разработки и другие ОС не обновляются.

Обновление требует опубликованного стабильного Release с файлами `setup.exe` и `latest.yml`. Артефакт Actions или draft/pre-release сам по себе не является каналом обновления. Для автообновления нужен опубликованный стабильный Release с `latest.yml`; старый Release `v1.0.0` таких метаданных не содержит. Обновить ранее установленную версию без поддержки автообновления нужно вручную, установив новый `setup.exe` из артефакта сборки.

Установщик **не подписан**. Контрольная сумма защищает от повреждения файла, но не доказывает автора, если скомпрометирован GitHub Release. Проверяйте владельца репозитория, ограничивайте доступ на публикацию релизов и включите двухфакторную защиту; для доверенной промышленной установки необходима цифровая подпись и её проверка.

### Публикация нового релиза для сопровождающего

1. Увеличьте стабильную версию в `package.json` и `package-lock.json`, протестируйте и включите изменения в предназначенный для релиза коммит. Версия должна быть выше опубликованной ранее.
2. После проверки создайте и отправьте тег `v<версия>` на этот коммит, например `v1.2.0`. Версия тега должна точно совпадать с `package.json`.
3. Workflow **Publish Windows release** соберёт программу на Windows, выполнит тесты, сверит хеш и версию метаданных с `setup.exe` и опубликует GitHub Release с обоими файлами. Для workflow нужны разрешения `contents: write`. Для каждой версии нужен новый тег; существующий Release не перезаписывается.
Можно также явно запустить публикацию коммитом с маркером `[publish-release]` в сообщении; обычные push релизы не публикуют.
4. Проверьте успешность workflow и доступность обоих файлов в публичном Release. Только после публикации этого релиза установленное приложение сможет найти обновление. Сборка на каждый push по-прежнему выдаёт артефакт Actions, но не публикует релиз.

### История и DHCP

В разделе **Подключение → Правила безопасности и история** можно отдельно включить запись на диск. В историю записываются до 100 видимых сигналов при каждом обновлении окна и пятиминутные агрегаты исходящего трафика по IP. События и агрегаты хранятся до 7 дней, общие суточные агрегаты — до 30 дней; лимиты — 10 000 событий и 100 000 агрегатов. Самые старые записи удаляются при переполнении. Сырые потоки не сохраняются. Очистить историю можно отдельной кнопкой; выключение записи не удаляет ранее сохранённую историю. При остановленном приложении устаревшие записи удаляются после следующего запуска. При заполнении диска или ошибке сохранения выводится ошибка. Обеспечьте защиту файла `security-history.json` в каталоге данных пользователя Windows и резервных копий.

По кнопке **Получить текущие DHCP-аренды** приложение выполняет разовый запрос `/rest/ip/dhcp-server/lease` к RouterOS 7 с введёнными пользователем данными. Учётная запись должна иметь права чтения. Сохраняются только активные однозначные аренды, снимок используется не более пяти минут. Текущая аренда не доказывает, что IP принадлежал тому же устройству в прошлом; данные об аренде, доступные в момент сигнала, могут сохраняться в истории, если она включена. Пароль на диск не записывается. При HTTP он передаётся без шифрования. DHCP не связан с приёмом потоков.

Нажмите категорию в блоке **Типы трафика**, чтобы увидеть до 100 источников и до 200 последних записей данной категории. Это предположения по портам, а не фактическая принадлежность к сервису.

## Базы репутации и плитки сигналов

Скачиваются два публичных IPv4-списка: [IPsum ≥3](https://github.com/stamparm/ipsum) (адреса, замеченные не менее чем в трёх исходных списках) и [Blocklist.de через FireHOL](https://github.com/firehol/blocklist-ipsets/blob/master/blocklist_de.ipset) (адреса из сообщений fail2ban). Списки могут пересекаться и не являются независимым подтверждением. Базы включены по умолчанию; их можно выключить, вручную обновить или очистить кэш в **Подключение → Базы репутации IP**. Через 15 секунд после запуска и далее примерно раз в сутки приложение запрашивает неизменяемые адреса GitHub API; при неудаче повторяет попытку примерно раз в час. Внутренние IP и потоки не отправляются: сравнение выполняется по локальному кэшу, но GitHub видит IP компьютера, скачивающего списки.

В интерфейсе указаны источник, количество адресов, дату свежести, время загрузки и ошибки. Для Blocklist.de дата свежести — более ранняя из даты исходного файла в заголовке и даты изменения файла в GitHub; для IPsum используется дата изменения файла в GitHub, поскольку исходная дата в нём не указана. Последняя не гарантирует свежесть исходных списков. Если дата свежести или загрузка старше 72 часов либо дата неизвестна, база не участвует в анализе. При временном сбое сохраняется последняя пригодная версия. При отключении загрузка и сравнение прекращаются, но кэш остаётся до очистки. GitHub API может ограничивать число запросов, а сети с корпоративными прокси могут требовать отдельной настройки доступа. Проверяются внешние IPv4 в потоках относительно заданных локальных подсетей; IPv6 и домены не поддерживаются. Совпадение означает только присутствие в списке и не определяет тип угрозы; не используйте его для автоматической блокировки.

Плитки **Возможный майнинг**, **Возможный спам**, **Возможный DDoS** и **Репутация IP** показывают число уникальных локальных хостов с действующими сигналами за 5 минут. Прочерк означает не настроенные подсети или недоступные базы репутации. При нажатии видны до 100 хостов и 200 записей, участвовавших в вычислении. Для DDoS это все потоки соответствующего направления отмеченного хоста — не каждый такой поток является атакой. Категории построены по метаданным, не изолируют и не блокируют устройства.

Дополнительные диаграммы показывают объём записей по времени их получения, распределение по направлениям, топ источников и до 14 дней, за которые есть сохранённые суточные агрегаты. Суточный график доступен при включённой истории; отсутствие записей за день не равно отсутствию трафика.
